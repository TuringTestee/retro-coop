# Project guidance

Use Vaseline to agree on what to build, divide it into dependent issues, and deliver reviewed changes. Product scope and technology choices still need user alignment.

- Start every human-facing document with a concise summary a second-year CS student can understand. Put technical detail afterward.
- Skills are linked from `.agents/skills/` to the pinned `tooling/vaseline` submodule. Read the named skill's `SKILL.md` if discovery is unavailable. Keep project-specific guidance here.
- Use `project-planner` with the user as CEO and the AI as architect. Keep behavior in `docs/design/<project>.md`, technical detail and the review snapshot in `docs/implementation/<project>.md`, and the actionable architecture/reuse decisions, priorities, dependencies and acceptance in the epic description. Strongly recommend careful review of the epic and planning PR.
- For user-facing delivery, keep a Project gate with multiple user journey stories from arrival through outcome and recovery, and trace every visible feature to its applicable journey. Require current integrated evidence before accepting the affected experience. For Retro Coop, remove interface content that does not help a player decide, act or understand game or session state.
- Require actual approval of the reviewed plan version and merged governing documents before execution. The planner owns decomposition; there is no separate breakdown stage or PR. Changes to agreed behavior or major constraints require renewed alignment.
- `project-orchestrator` reads the approved epic, creates or reuses child issues, and organizes GitHub Projects when accessible or uses issue-only tracking otherwise. Missing Project access does not block eligible work or require another approval. Verify live ownership, real blockers and integration evidence before dispatching `issue-resolver`; priority never overrides dependencies.
- Use `pr-testing` and `local-pr-review` before PR handoff. Substantive changes require a fresh reviewer with no inherited builder context, a separate detached worktree, and only the PR URL and review instructions as input. Publish evidence following [the handoff contract](tooling/vaseline/docs/review-handoff.md).
- Before implementation, ask whether the user wants A) review of every PR manually or through another bot, or B) agent merging after local review and passing tests, unless an explicit choice already covers this scope. Without an answer use A; never record silence as consent. Keep actual choices in the main checkout's ignored `.agents/preferences.local.json` using [the shared preference format](tooling/vaseline/docs/local-preferences.md), and pass scoped authorization to worktree agents. Preserve existing preferences; conflicts require clarification before using B.
- Use the merge policy recorded in the epic. The user has authorized agents to merge this project's PRs after local review and passing required checks; do not ask again for each PR. Preserve branch protections and planning/scope approval, and confirm integration before starting dependent work. Without scoped authorization, require external review and a separate merge owner.
- Run the README's pre-flight command in under one minute. Keep presubmit CI under 30 minutes with a hard timeout. Separate post-submit E2E or soak tests may run for hours. Add suitable focused tests and evolve pre-flight when the project gains executable features; no language or framework has been chosen.
