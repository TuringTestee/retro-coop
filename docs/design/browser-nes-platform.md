Audience: Human

# Browser NES lobby platform

Retro Coop lets visitors browse live game sessions, drop a legally supplied NES ROM to host a session, and play together while each browser runs its own copy. Included homebrew games remain available to start, even when no players are online. Servers list lobbies and connect people; they do not run games or receive user ROMs.

The [included-games amendment](included-games.md) governs the two ordered included choices, license placeholders and arbitrary-NES admission clarification; it supersedes earlier singular-featured wording and the initial blanket file-size ceiling where they conflict.

The [lobby experience amendment](lobby-refactor.md) proposes replacing special launchers, automatic solo start, and browser-created-only rooms with one directory and empty service-created rooms. Once its reviewed version is approved and merged, it governs those affected interaction rules; the remaining architecture, privacy, and release criteria here continue to apply.

## Status and alignment

The original approved planning revision incorporated the user’s request for registration-free internet play, minimal setup, friend discovery, conversational voice, and broad NES compatibility. PR #3 merged the approved baseline; the linked included-games amendment has its own review and approval record. The user requested a homepage showing all hosted sessions, drag-and-drop hosting, and an always-available special Tetris variant. They accepted delegated choices for staffing, budget, technology, and a first release with two-player deterministic delayed-input netplay. Final approval applies to the reviewed document revision, not earlier conversational assent.

The [UI design](browser-nes-ui.md) supplies text wireframes, the critique/revision record, and stories S01–S37 mapped to this document's acceptance criteria. It describes the visible states for both players, including failure and recovery; it does not replace the engineering or content gates below.

The user has supplied the included games and their distribution direction. The [catalog amendment](included-games.md) owns their order, placeholders and exact-content scope; runtime qualification remains evidence-based.

## Users, outcome, and boundaries

The initial audience is friends and portfolio visitors on desktop browsers who want to discover a session and play without installing software. The release is a free portfolio demonstration, with no billing or monetization. Success means two independent visitors can discover or share a lobby, load the same supported game, take separate controller slots, play in sync, chat, and recover from a short disconnect.

Planning assumptions are one developer assisted by coding agents, a prior 8–12 week estimate now subject to re-estimation for the expanded compatibility/voice scope, a $50/month operating target, and a $100/month ceiling. These are engineering envelopes, not purchased infrastructure or a delivery guarantee. The initial capacity envelope is 20 concurrent two-player sessions and 100 directory connections; it must be validated against measured relay use and current vendor prices before deployment. Start with the current stable desktop Chrome and Firefox on Windows and macOS; record exact tested versions for each release. Safari, mobile, and touch controls remain later goals. Broad NES compatibility is now an explicit release investigation and qualification workstream; the previous one-title-only validation is insufficient. Universal compatibility is not asserted before evidence.

The first release includes public and unlisted lobbies, two player slots, keyboard/gamepad mapping, local saves and export/import, a bounded rewind history, nearest-neighbor and scanline display options, text chat, opt-in conversational voice with optional push-to-talk, automatic readiness, controller assignment, and reconnect. Gameplay spectators, accounts, recordings/transcripts, cloud saves, passwords, public matchmaking, host migration, video streaming, rollback, and additional consoles are deferred. A full lobby remains visible with its status but cannot admit a third participant.

## Discovery and hosting

The homepage has the persistent [included-games choices](included-games.md), followed by the live public session directory. Each choice offers joining an available session or creating a new one. It is not a fictitious occupied lobby or a server running the game continuously. Until authorized content is configured, development builds show an unavailable placeholder; public launch requires the real game.

The directory exposes every active public session within the admitted capacity, including full, waiting, playing, and reconnecting sessions. Show a generated or host-edited room label, host nickname, unique public room code, occupancy, and status. Search public rooms by label or nickname and resolve an exact public code; keep full and reconnecting matches visible. Search has explicit no-match, stale, and service-error states. Duplicate nicknames are not identities; the room code or invite distinguishes a friend’s session. Multiple sessions of the same game stay distinct. Empty state retains both catalog launchers and an accessible file picker as well as a drop target. Unlisted sessions are accessible only through their invite and are excluded from directory results and events.

A dropped file is read and validated locally before creating a session. Reject malformed files, archives, unavailable-memory cases and unsupported mapper/region combinations with a clear explanation. Arbitrary iNES and NES 2.0 titles remain eligible without a catalog or blanket 8 MiB admission gate. The game label is editable and unverified for user ROMs; filenames, filesystem paths, artwork, and ROM-derived text are not automatically published. The drop target visibly states “Creates a public room; your file stays here” and offers an Unlisted toggle before selection. Public is the fresh default; do not silently restore a previous visibility choice. Drop/picker completion creates the selected kind of room without a naming dialog. Generate a neutral room label and guest nickname without using file content or filename; editing either is optional in the room. The UI says that players need their own matching file.

Joining reserves the available controller slot and opens the lobby before ROM selection. Guests need no account, email, nickname form, or controller-setup wizard. Assign host P1 and joiner P2 by default. A pending first-time join has a 120-second reservation lease; expiry releases the slot with an explicit Retry join action, without creating a reconnect entitlement. Rate-limit repeated reservations. The reservation becomes established membership only after the shared start/join barrier succeeds; failures retain the original lease deadline. The reconnect grace below applies only after that promotion. The joiner chooses a local file; only its SHA-256 hash and compatibility metadata go to the coordinator. Hash the exact file bytes; even header differences produce a mismatch, with an explanation. Do not normalize away differences. For either authorized catalog game, fetch its pinned asset directly into each browser and verify its manifest hash. Never fetch a user-supplied URL.

## Lobby and session lifecycle

Anonymous guests get server-issued sessions; display names do not establish identity. The host owns slot assignment, shared timeline changes, visibility, kick, and close. Initial start is automatic after both clients meet prerequisites and have active play intent. A guest may leave, cancel play intent, mute, and propose a pause. Both players must have matching ROM hash, pinned core build, state schema, and emulation settings before automatic readiness. Clicking Join or dropping/choosing a file expresses play intent; cancellation, a failed prerequisite, membership changes other than the expected reserved-to-established promotion, or assignment changes clear it. Choosing a replacement file or Retry renews intent; background retries cannot restore cancelled intent. Do not require separate Connect, Load, Ready, and Start clicks for a fresh shared start. The host can swap controller assignments only while paused or waiting; doing so clears readiness and requires both players to accept the changed assignment before resume. Membership and assignment changes are server-authoritative and atomic.

The observable lifecycle is waiting → ready → playing → paused/reconnecting → playing or closed. Start is an acknowledged barrier at a common initial state. The host starts solo immediately after successful local loading and room creation. A join reservation alone does not interrupt solo play. Once the guest’s ROM and connection are ready, pause at a committed frame and offer the host Continue current game, Restart together, or Keep playing alone (releasing the pending guest with an explanation). Continue transfers validated dynamic state to the guest and preserves progress; Restart requires both players’ explicit agreement. A failed transfer retains the host’s old timeline paused and offers retry or resume solo. The guest sees waiting for host and may cancel. No late join resets or replaces progress automatically. A room still at its initial state can start both players automatically through the shared barrier.

Heartbeats are sent every 10 seconds. After 30 seconds without a heartbeat, reserve the slot and show reconnecting; the client also pauses immediately when the input stream cannot progress. Allow a 60-second reconnect grace period from detection, authenticated with the original session token. A returning player reloads the matching ROM if needed, receives a validated checkpoint, and both acknowledge resume. If the host does not return, close the lobby; if the guest does not return, free their slot and leave the host paused with an option to resume solo. Explicit host closure removes the listing immediately. A coordinator restart closes its ephemeral lobbies and clients return to the directory with an explanation.

## Local emulation and synchronization

Use a pinned emulator behind an adapter for frame stepping, input, deterministic state export/import, and battery RAM. JSNES is the first candidate, not a compatibility guarantee. Its documented APIs support frame stepping and state serialization ([upstream API](https://github.com/bfirsh/jsnes#api-reference)); cross-browser determinism, mapper state completeness, and safe serialization still need an early experiment.

Each client sends controller inputs tagged with session epoch and frame number over an authenticated WebRTC data channel. Begin with reliable ordered delivery and a negotiated fixed input delay, initially 3–8 frames for the 60 Hz target. Advance only when both inputs for a frame are known. Missing input stalls simulation and presents network status; never silently predict or skip emulated frames. A slow/background client pauses the shared game. Display filters and device audio scheduling do not alter canonical emulation settings.

Compute a canonical state hash every 120 committed frames. Compare only identical epoch/frame pairs; wall-clock timestamps, rendering buffers, transport counters, and local audio queues are excluded. On mismatch, pause and allow one automatic bounded resynchronization attempt using the host's last agreed checkpoint plus subsequent inputs. If validation fails or mismatch recurs, keep paused and offer a coordinated reset or exit. Peers exchange dynamic machine state only after matching the ROM and core fingerprint.

State formats need an allowlisted, versioned schema. Reject unknown fields, non-finite numbers, wrong array lengths, incompatible fingerprints, and payloads over the measured limit (initial upper bound 2 MiB). Reconstruct immutable ROM mappings from the receiver's local file: generic emulator dumps can contain copies of cartridge bytes. Never send the raw emulator object, ROM buffers, or immutable cartridge regions. Chunk transfers to at most 16 KiB, impose backpressure and a 10-second timeout, and fail closed on invalid state. WebRTC data is encrypted in transport ([MDN data channels](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Using_data_channels)); this does not make peer data trustworthy or prove state dumps exclude ROM content.

An initial shared reset uses known battery RAM, not each player's unrelated local save. Any existing save must enter through the coordinated restore flow. Keep emulation frequency, audio emulation settings, mapper behavior, and core version identical. A lobby pins its build; deployments must retain matching static assets for existing sessions.

## Saves, rewind, and controls

Local battery RAM, save slots, mappings, and preferences live in IndexedDB, keyed by ROM hash and core/state version. Save creation captures a committed frame locally without changing the timeline. Export/import allows users to back up compatible saves. Show storage errors and offer export; do not promise persistence after browser eviction or site-data deletion ([MDN storage lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). No server save upload exists in this release.

Solo play supports a rolling 10-second rewind target, bounded by a 32 MiB memory budget. If a supported game cannot meet that target, the prototype must propose revised scope rather than silently reduce acceptance. Multiplayer rewind is a host-requested jump up to 10 seconds back, accepted by the other player; it is not independent scrubbing. Restore and reset use the same pause/propose/accept barrier. After both acknowledge the checkpoint, increment the epoch, discard future input/history, and resume; rejection or a 15-second timeout leaves the old timeline paused. Only validated compatible saves may be proposed.

Provide remapping with conflict feedback and restore-default controls. Losing focus releases held inputs; gamepad disconnection pauses and offers keyboard fallback. Suppress game input while typing chat. Audio begins after a user gesture. Lobby controls are keyboard accessible, have readable focus states, and communicate status without relying on color.

## Social features and abuse controls

Text chat uses the authenticated lobby WebSocket, with a 500-character message limit and five-message-per-10-second guest rate limit. Escape text; support no HTML or attachments. Retain at most 100 messages in memory for current members and delete them when the lobby closes. Joining clients receive no pre-join chat history. Voice is opt-in between the two players. Enable voice requests browser permission and starts conversational open-mic mode; optional push-to-talk remains available. Show persistent microphone/transmission status, local mute, separate remote-audio mute/volume, and an accessible input-device selector with a default device. Request echo cancellation and noise suppression where available; do not claim browser processing eliminates echo. Microphone denial, missing/unplugged devices, or failed voice negotiation leave gameplay/text usable and offer retry. Blur releases push-to-talk and mutes open mic; returning focus requires deliberate unmute. Leave, kick, expiry, or peer replacement stops microphone tracks and voice connections; reconnect never silently unmutes. Voice reconnect can retry without resetting emulation. Do not record or transcribe.

Kick revokes the guest's membership and reconnect permission; the other client closes that peer connection. Rate-limit lobby creation, joins, and signaling. Unlisted invitations use at least 128 bits of unpredictable entropy and do not appear in analytics or referrers. Validate WebSocket origin, membership, message schema, and authority for every operation. Tokens are secrets, not display-name claims. Public anonymous moderation cannot prevent every returning user; provide operator lobby removal and temporary admission blocks without adding accounts to this release.

Direct peer connections can disclose participants' network addresses. Explain this inline beside Drop/Join before connecting and provide a relay-only privacy option there and in Settings, subject to relay availability and capacity. The action accepts the displayed Standard default or selected Relay only policy; do not insert a separate connection modal. If either player chooses relay-only, both ends apply it before gathering/sharing peer candidates; never fall back to direct against that preference. ICE/TURN fallback is needed where direct connectivity fails ([MDN connectivity](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Connectivity)). Relay servers forward encrypted traffic and still do not emulate the game.

## Architecture and data ownership

Use TypeScript with React/Vite for the client, a Node.js service for directory/lobby WebSockets and signaling, and managed STUN/TURN or a separately operated TURN service. Select specific versions and providers after the feasibility and price checks. Prefer a single coordinator instance with in-memory lobby state and a static client/catalog served over HTTPS. No production database is needed for ephemeral sessions. Emulator work runs in a worker behind the adapter; the page owns input, canvas presentation, and audio output.

The coordinator stores only guest membership, user-entered labels, scoped ROM hashes/fingerprints, readiness, and short-lived signaling/chat. ROM hashes are not ownership evidence and are not exposed in the public directory. Reject binary uploads and unexpected request fields; infrastructure request-body logging is disabled. Do not send ROM content, saves, chat text, SDP, tokens, filenames, or microphone audio to analytics. Authorized catalog assets are a separate deployment artifact with provenance, licence text, credits, and pinned hashes.

Delete ephemeral lobby data on closure, expire unused guest sessions after 24 hours, and retain redacted operational events for seven days. Clients offer local-data deletion. Operator configuration and catalog manifests are version controlled; back up deployment configuration and secrets in the chosen provider's secure mechanism. Ephemeral lobbies have no recovery guarantee across a server restart. Document restores before launch.

## Content policy

The catalog may include only games with explicit redistribution and browser-play permission or a licence covering distribution of the actual ROM and included assets. Keep the evidence and attribution with each asset. Free-to-play availability elsewhere is insufficient. Bring-your-own-ROM sessions never share their file through the platform, including through resync. There are no third-party ROM download links, supplier maps, automatic downloaders, or user ROM storage endpoints.

The [catalog amendment](included-games.md) records the supplied titles, user authorization and requested license placeholders. Verify actual binary behavior before advertising a multiplayer mode; do not invent license terms.

## Fast-start contract and compatibility

“One click” means one application Join/Play action when the game is included or already loaded in that browser tab, with automatic nickname, controller defaults, connection, matching, and initial start. It does not include bypassing browser permissions or supplying a missing local file. User ROM bytes remain in memory only; do not persist ROMs in IndexedDB to manufacture a returning-user shortcut. Saves and preferences persist as specified above. An invite opens a room preview with Join; it must not capture microphone input or publish peer addresses merely by opening a URL. Catalog Join automatically fetches the pinned asset, without a separate Load action. Enable sound may be needed if the browser blocks audio after asynchronous loading; preserve play rather than rerun setup. Browser microphone permission remains an explicit voice exception ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)); browser audio restrictions also apply ([MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)).

Use an 8-character unambiguous public room code, unique among active public rooms and allocated atomically with collision retries. It is a discovery label, not a credential. Unlisted rooms have only the high-entropy invite and never resolve through public code/search endpoints. Keep nickname and label limits at 32 and 80 characters respectively, render as plain text, and search case-insensitively over admitted public rooms. Do not expose hashes to make discovery work.

The product goal is broad NES file support beyond the two catalog games. P1 must compare candidate cores using documented format, mapper/submapper, region, peripheral, battery RAM and state support plus measured cross-browser deterministic replay. Publish separate local-play and netplay qualification statuses, with unsupported and untested distinguished. Do not reject a structurally valid file solely because its title is unknown: use supported hardware/header metadata for admission, and label unqualified combinations experimental rather than tested. Detect unsupported hardware before creating a misleading playable listing. A compatible file may still fail during emulation; pause, preserve available saves, explain the failure, and offer exit/report without ROM upload. No automatic fallback to another core or streaming mid-session.

The qualification inventory must enumerate the selected core’s implemented mapper/region combinations and all known gaps. Every combination advertised as supported needs an authorized representative fixture with local boot/input/audio, battery save where applicable, state roundtrip, rewind, and the AC-05 cross-browser netplay profile. Record fixture provenance and exact hashes in developer test data, not the public directory. Where fixtures are unavailable, mark unverified rather than invent passing evidence. Include header/format variants, malformed files, resource-exhaustion cases and unsupported peripherals in negative tests. The structural validator and measured browser resource budget own file admission limits as specified by [Included games and arbitrary NES files](included-games.md); there is no blanket size ceiling or title allowlist. Archives, disk-system formats and nonstandard controllers are not silently included by “all NES.” A concrete qualified matrix and its exceptions must be reviewed before compatibility/launch scope is accepted; the old 8–12 week estimate is provisional pending this larger inventory.

Netplay reproduces the original game’s behavior. Simultaneous two-player titles use P1/P2; alternating-turn titles retain their native turns. Single-player games do not become co-op. Provide an optional shared-controller session mode: one guest at a time owns P1; the host requests transfer while paused, the recipient accepts, held inputs clear, and ownership changes atomically before shared resume. No simultaneous writers to P1. Default remains separate P1/P2; session mode is optional settings, never a required onboarding question. Zapper and other special peripherals need explicit qualification or an unsupported explanation.

Proposed performance acceptance (to measure, not a claim): on the release desktop browser matrix, a 10 Mbps connection and AC-05’s 100 ms RTT/20 ms jitter/1% loss profile, p95 drop-to-controllable-solo is at most 3 seconds for each representative local-file size cohort in the reviewed compatibility matrix; p95 included-game Join-to-shared-controllable-frame is at most 10 seconds for each exact cold catalog download. These timing cohorts measure performance and do not create an admission ceiling. For local-ROM joining, measure from successful file selection and report earlier user selection time separately. Host choice/browser permission time is reported separately from system work, never hidden as a fast completion. Measure at least 30 attempts per browser pair and direct/forced-TURN route, with at least 29 successful connections per cell; report failed attempts as failures and all successful durations. Voice enable/permission-grant-to-audible-remote is p95 at most 5 seconds over 30 attempts per route. Test public internet peers on two independent networks, including forced relay, alongside controlled impairment. If these proposed budgets fail, fix the path or explicitly revise the commitment before launch.

## Operations and future scope

Use local and staging environments before a small public beta. Monitor active sessions, join/connect failures, TURN bytes, stalls/desync counts, process health, and client error codes without content. One developer owns alerts, abuse reports, rollback, and the post-launch review. No staffed 24/7 availability promise is made. A client can continue solo offline after coordinating exit from multiplayer.

Before spending, confirm vendor quotas and prices and set enforceable relay quotas/admission limits; alerts alone cannot guarantee a bill ceiling. If a provider cannot enforce limits, do not deploy under the $100 ceiling without a revised choice. Preserve established sessions when capacity permits and reject new admissions clearly. Reassess after the first two weeks of beta using connection success, completed sessions, recovery frequency, and measured cost, with no raw play/chat recording.

Rollback netplay, more supported games, gameplay spectators, mobile/Safari, passwords/accounts, and cloud saves remain provisional. Host video streaming is a separate architectural option requiring renewed alignment; it is not an automatic fallback if determinism fails.
