# Local battery progress, preferences and recovery

Battery-backed games now resume their saved cartridge RAM when the player selects the same compatible ROM again. Local controls, display and volume preferences survive reload, and Local data lets players export or delete current and older records. ROMs are never persisted. This is a bounded part of D06; [measured local rewind](d06-rewind.md) follows separately, and remaining state-profile qualification is still open.

## Ownership and behavior

Rust `local_file::identity` remains the exact battery/save compatibility owner: ROM hash, core hash, schema, resolved region/settings and cartridge layout are covered. `local_file::info` supplies both codecs' identity and the existing Rust-owned byte limit; neither browser consumer copies that policy. `local_has_battery` reads the loaded cartridge's battery flag. Local loading stays independent of whole-state save-profile support.

The worker's correlated file-operation path handles `battery-info`, import and export. `LocalPlayer.fileRequest` uses the same request/worker ownership for active and candidate workers. Before a candidate can become active or receive its first frame, the player reads its exact battery identity and imports any stored bytes through the existing bounded, transactional Rust decoder. Corrupt, incompatible, denied or unavailable storage reports a recovery message and preserves the record while allowing the ROM to run. Failed restore disables automatic replacement of that record; the player can export it in Local data, delete it explicitly and retry saving current memory. A successful imported battery is restored progress, not pristine state for future shared-start admission.

After any room-selection confirmation, replacement waits for the old game's current battery write to complete before reading the candidate identity. Concurrent lifecycle/timer captures await that same write promise. This prevents reselecting the same ROM from importing an older record before its outgoing capture commits.

An actual ten-second browser timer captures current battery progress. Visibility loss, window blur, page hide and successful game replacement also request a capture. These are best-effort lifecycle opportunities: unloading can terminate asynchronous work, so the interface never promises that closing a tab durably saves its final instant. Storage success means transaction completion, not request success. Failure leaves the running game available and exposes current battery export. Download initiation is reported as requested; the browser controls the actual file write.

`saves.ts` remains the sole IndexedDB owner. Version 2 adds `batteries`, `preferences` and a `meta` generation counter while retaining version-1 manual slots unchanged. Battery records contain only identity, timestamp and bounded ROM-free bytes. Preferences contain identity, timestamp and controls/filter/volume. The shared fingerprint `fileIdentity` owns the preference compatibility tuple and existing room file matching consumes it too. Stored preferences must pass the shared control action/conflict rules and preference validation; defaults are never written merely by reading. Explicit user edits are serialized, and late reads cannot replace newer edits or apply to a different game. Audio remains opt-in for each page; microphone/connection privacy settings keep their existing owners.

Automatic battery writes compare the previously loaded bytes and timestamp atomically, preserving another tab's newer data. The shared comparison uses `Object.is` for timestamps, so an unchanged damaged `NaN` timestamp can be explicitly deleted without treating `NaN` and `null` as equal. Preference deletion applies the same timestamp check before its value comparison. `validSavedAt` owns timestamp validity for normal slot listing, display and battery autoload; malformed metadata disables automatic battery persistence and remains available for explicit recovery. Battery retry also reuses the full expected-record comparison, including bytes, rather than trusting a timestamp alone. Manual save and battery deletion share that expected-record comparison; preference deletion compares its displayed value and timestamp in the same transaction. Local data refreshes its list after a failed mutation so the player can make a new informed decision. Confirmations can be cancelled with Escape, restore focus to their trigger and do not silently replace newer records.

Clear-all removes slots, batteries and preferences in one transaction and advances the shared generation. Already-running tabs cannot recreate cleared records through old automatic work. The current tab stops automatic persistence before clearing; resuming writes requires explicit retry, a new preference edit, or ROM selection. Current play stays in memory. This is local data removal, not server-account deletion. Reads and transactions have bounded five-second storage waits; blocked upgrades report a retry instruction. A clear failure is visible, and the player can retry battery saving.

Local data is reachable from Settings and storage-error recovery. It lists all stored identities, labels those matching the current game/build, and exports older or corrupt bytes without pretending the current core can restore them. The export buffer remains in memory for retry if download initiation fails. Browser eviction and external site-data removal may erase storage; an empty database is described as empty, not claimed to prove detected eviction. ROM selection remains required after reload.

## Evidence and reproduction

Run the README preparation, `timeout 60s sh scripts/preflight.sh`, and `python3 scripts/foundation/browser_smoke.py --chrome --output /tmp/foundation.local.json`. `persistence_smoke.py` extends the existing actual-WASM browser workload; CI's existing `foundation.local.*.png` artifact pattern includes its Local data screenshots. There is no new job or increased deadline.

The browser fixture reads battery RAM at boot into CPU RAM, writes nonzero progress, waits for the real ten-second timer, reloads through the UI, and independently inspects exported machine state to prove that the CPU saw restored battery data before its first instruction. It also proves v1 slot preservation, exact-game preference restoration, raw other-identity export, corrupt-record preservation/recovery, cancellation, cross-tab generation protection, denied-storage play/export, no ROM fields in database records and no outgoing file upload. Older identity coverage uses an explicitly synthetic identity, not a claim of testing an unavailable historical core.

Desktop before/after and mobile screenshots show the real Local data panel. Existing slot, controller, display, worker and native codec checks run alongside this coverage. Development harness failures are retained: the first inspected cartridge RAM instead of CPU work RAM for the boot-read assertion; the second attempted a second page through Playwright's single-page convenience context. A later preference assertion matched both Right and Shift Right; scoping it to the exact Change Right control corrected that selector. These were corrected in the harness, not hidden as passing results.

Remaining mapper qualification and coordinated shared-game restore are also not claimed here. The established state-restore audio filter/synth epoch limitation is unchanged; arbitrary PCM continuity is not promised. D06 stays open.
