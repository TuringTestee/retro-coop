# Manual local save slots

Players can keep three manual save slots for the current compatible game, restore one after confirmation, and import or export ROM-free backups. Saving and importing into storage do not replace the running game. This is another bounded D06 slice: automatic battery/preferences persistence, local-data management across versions, remaining mapper qualification and measured rewind remain open in issue #10.

## Ownership and safety

`local_state::candidate` owns complete file decoding and validation. Restore commits its returned Bus; `validate_file` discards it. The validation-only path therefore uses exactly the same allocation, identity, mapper and hardware rules without changing live progress. `local_state::info` returns the Rust compatibility identity and the existing Rust-owned cap. The worker exposes correlated `state-info` and `state-validate` operations alongside the existing export/import operations. No TypeScript envelope decoder or second compatibility/size policy is introduced.

`LocalPlayer` owns pending file requests, keyed by monotonically increasing request IDs and the actual worker. Replacement, cancellation, fatal worker failure and disposal reject pending requests; late replies cannot resolve a new request. File operations have a ten-second response deadline. Read operations do not pause the timeline. Confirmed load pauses, imports transactionally, releases input and flushes presentation audio, then leaves the game paused for explicit Resume. The existing audio-epoch limitation still applies; see [the state boundary](d06-state.md). Peer/shared-game restoration remains the later coordinated-barrier obligation.

`saves.ts` is the sole IndexedDB owner. Database `retro-coop-local`, version 1, contains `saves` records keyed by `[identity, slot]` and indexed by identity. Each record contains only compatibility identity, slot number, saved timestamp and validated machine bytes. No filename, ROM, PCM or screenshot is persisted. Save/import remain disabled until listing succeeds. Each write checks the previously displayed slot in the same read/write transaction before replacing it, so another tab cannot bypass overwrite confirmation through stale UI. A request's success is not durability: promises resolve on transaction completion and reject on abort. Connections close after each operation and on version change; blocked opening reports a retry instruction. Existing incompatible identity records are retained, not migrated or silently deleted; cross-version management remains a later Local data slice.

The panel checks the Rust-owned limit before reading imported files, validates through the current worker before insertion, and confirms occupied-slot replacement. Invalid imports do not overwrite a slot or load a timeline. A load remains subject to the worker's full compatibility validation even if bytes came from IndexedDB. An unsupported save profile reports that limitation without blocking local play. Slot deletion and timeline loading require confirmation; Escape cancels a confirmation before closing the panel, and focus returns to the initiating control.

Storage denial, quota errors and aborted writes retain a memory backup and expose export. Export failures retain those bytes for retry. Download initiation is reported as requested, not as proof that the browser wrote a file. Site-data deletion or browser eviction can remove records; an empty store is described as empty, not claimed to be detected eviction. ROM selection is still required after reload.

The real WASM/IndexedDB smoke exercises non-disruptive save, overwrite and deletion confirmation/cancellation, reload with explicit ROM reselection, confirmed restore, import without timeline mutation, wrong identity/malformed/oversized input, transaction abort after request success, memory export after failure, storage denial, unsupported profiles and stale-worker replies after replacement. ## Remaining D06 acceptance

This implements U6's manual compatible-slot path under [issue #10](https://github.com/TuringTestee/retro-coop/issues/10), [the approved UI](../design/browser-nes-ui.md#u6--saves-and-local-data) and [the implementation plan](browser-nes-platform.md), approved at `2e8adfcd3259f5bdffdc9a13ef9b983f78cfb965` and merged through PR #3 (`ecf6bd4c7443526f0a163b721a351c854ee90fd4`). Its validated state prerequisite is PR #49, integrated at `039afc9`; battery ABI was PR #47.

Battery/preferences persistence and full Local data management remain separate. Rewind must use actual regional emulated duration and measured retained allocations: the prior real-worker MMC1 state was 96,616 bytes, so 602 copies alone require 58,162,832 bytes (55.47 MiB), above the 32 MiB budget. Sparse checkpoints plus input replay are the next candidate implementation, not current proof. D06 cannot close until its ten-second memory-bounded rewind and remaining agreed outcomes are delivered; no fixed 600-frame or rounded-60-fps substitute is accepted.
