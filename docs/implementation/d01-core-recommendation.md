# D01: NES core and fixture inventory

Recommend the pinned TetaNES core for the bounded feasibility experiment. It offers broader hardware and timing coverage than JSNES and separates cartridge ROM from serialized memory. These are source observations: no Retro Coop game, browser pair, state codec, or hardware combination is qualified yet. The revised planning range is **16–24 developer weeks**, conditional on D02 passing and authorized content being supplied; unsupported hardware additions remain separately estimated proposals.

## Selected hardware inventory and limitations

Each of the 42 IDs in the JSON has global NTSC/PAL/Dendy timing availability and **untested local play / untested netplay**. There are 126 mapper/region combinations before splitting submappers, RAM layouts and peripherals. Mapper 34 has two dispatch rows (CHR size below 16 KiB selects BNROM; otherwise NINA-001). Its internal serialization discriminator 4096 is not an NES mapper number. The complement of the listed IDs within 0–4095 is absent from selected dispatch; this includes unassigned numbers, not 4,054 identified missing boards.

Source: [mapper registration and loaders](https://github.com/lukexor/tetanes/blob/a0a6b17f8ba9c5ee451453fb2409753fd06e5a31/tetanes-core/src/mapper.rs). Broad families include NROM, MMC1/3/5, UxROM, CNROM, AxROM, MMC2/4, Color Dreams, Bandai FCG, Jaleco, Namco, VRC2/4/6, Taito, BNROM/NINA, GxROM, FME7, Camerica, NES-EVENT and FK23C. Notable absent IDs include 20 (FDS), 28/30 (homebrew boards), 32, 65, 67, 75, 78, 80, 85 (VRC7), 118/119, 163 and 232; the JSON complement rule covers the remaining absent IDs without pretending to enumerate every physical board variant.

Submapper dispatch is not universally enforced. Inspected specific cases include MMC1 submapper 5, Bandai 16 submappers 4/5, VRC4 21 submappers 1/2, VRC2/4 23 and 25 submappers 1/2/3, Camerica 71 submapper 1 and Namco 210 submappers 1/2. VRC loaders fall back to combined address-line decoding for other values; Namco can auto-detect; mapper 34 uses CHR size. These observations are **not** a promise that other values are valid or safely rejected. D05/D20 need reviewed board metadata rules and explicit unsupported/experimental explanations, while admitting unknown titles on eligible hardware.

## Adapter feasibility observations for D02

The [core API](https://github.com/lukexor/tetanes/blob/a0a6b17f8ba9c5ee451453fb2409753fd06e5a31/tetanes-core/src/control_deck.rs) exposes `load_rom`, `clock_frame`, frame buffers, audio samples, SRAM and serialized-state methods. Use the core crate behind a WASM boundary; React/Vite/TypeScript and browser-local emulation remain the approved architecture. A `cdylib` declaration and upstream browser frontend do not prove our exports, worker loading or audio path work.

D02 must investigate WASM exports and copying costs, worker initialization and transferable frame buffers, deterministic sample production versus Web Audio playback, pause/throttling, and Chrome/Edge/Firefox replay. Explicitly set RAM initialization (default is random), region, emulation options and run-ahead behavior. Browser playback volume/resampling must not change emulated timing. Do not import upstream filesystem/localStorage persistence into the user-ROM path.

The [memory serializer](https://github.com/lukexor/tetanes/blob/a0a6b17f8ba9c5ee451453fb2409753fd06e5a31/tetanes-core/src/memory.rs) writes the mutable tail and layout metadata, then restores cartridge bytes from local memory. This is a useful starting point, **not ROM-free checkpoint proof**: D02 must audit the entire bus/CPU/PPU/mapper representation and reject malicious lengths, ranges, discriminants and payloads before allocation. CRC32 identity in upstream state is insufficient for the required SHA-256 protocol fingerprint. `deserialize_state` ignores trailing bytes and clears input; the adapter must define exact consumption, committed-frame controller/latch behavior and replay restoration. Never transmit unchecked upstream state dumps. Measure the required 10-second/32 MiB rewind and 2 MiB checkpoint envelope rather than deriving a promise from source comments.

The inventory pins **AccuracyCoin** commit `9bc42d1e3acbeeaea215b1011d58f4ce72a8a49e`, the actual 40,976-byte `AccuracyCoin.nes` and its SHA-256 `7e25ac08d2e7ed14c9b1f16bd853148fef09a824452164f8e0d69fd2bd96176c`. Its [author README](https://github.com/100thCoin/AccuracyCoin/blob/9bc42d1e3acbeeaea215b1011d58f4ce72a8a49e/README.md) identifies an NROM diagnostic targeting NTSC CPU/PPU revisions. The repository [MIT license](https://github.com/100thCoin/AccuracyCoin/blob/9bc42d1e3acbeeaea215b1011d58f4ce72a8a49e/LICENSE) supplies permission evidence; preserve Chris Siebert's notice and permission text with future copies. D01 inspected bytes and provenance, not emulator test outcomes. Prebuilt hash reproducibility is recorded; rebuilding the bundled assembly toolchain was not attempted.

This fixture can start CPU/PPU investigation, but cannot establish two-player gameplay, every NROM layout, battery persistence, PAL/Dendy, other mapper families or peripherals. Every other selected family explicitly has a fixture gap. Do not inherit permission from third-party ROMs bundled with emulator tests or scrape commercial games. D20/content owner must pin representative authorized diagnostics/homebrew and rights per advertised combination; D03 separately resolves the actual featured title. D05/D20 should create original negative header/truncation/size/unsupported-hardware test inputs. No runtime fixture downloader or ROM-sharing endpoint is introduced here.

Core licensing inventory: selected TetaNES declares MIT OR Apache-2.0; choose MIT when packaging the core and retain its copyright/permission notice. JSNES declares Apache-2.0 and binjnes MIT. D02/D04 must inventory the actual locked transitive dependencies and their notices in the resulting distribution, plus any modified-source notices required by chosen licenses. An upstream core license does not authorize its example ROMs/artwork or the featured title.

## Revised effort and gates

This is an engineering range for one developer with agent assistance and independent review, not a measured completion date. Budget **16–24 developer weeks** for the existing release behavior: feasibility/inventory 1; foundation/local play/saves/controls 3–4; room lifecycle/discovery/text 2–3; connectivity/synchronization/recovery/shared timeline 4–5; voice/authorized content integration 2–3; compatibility fixtures, staging, cost and combined release validation 4–8. The sum is 16–24. It includes review/fix time and WASM/worker/audio integration within the foundation and networking allocations; agent concurrency does not eliminate those responsibilities.

The increase from 8–12 reflects inspected format/state integration gaps, 126 initial mapper/region cells before variants, absent licensed fixtures for almost all hardware, and retained voice/recovery/journey/cost evidence. It assumes D02 passes, the chosen qualified subset is reviewed against the broad-support goal, and the user supplies the featured artifact promptly. Waiting for rights, new game development, or implementing missing mappers/peripherals is excluded and can extend calendar time; estimate each such proposal separately. Do not use the upper bound as a universal-hardware promise.

Preserve the approved five-developer-day **combined initial feasibility package** limit: record D01 time against it and give D02 the remaining budget, not a fresh five days on top. D02 owns runtime measurements and a pass/fail/realign report; it must stop and report unmet evidence at that bound. Reassess the range after D02 and again after shared networking. Foundation work waits for integrated D02 evidence. AC-15 remains open until D20's reviewed qualification matrix and D15's gameplay-mode evidence; no title or hardware support is advertised by this PR.
