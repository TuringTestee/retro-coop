# Load games from ZIP files

Players can drop a ZIP or select it in the existing game picker. The server extracts its NES game automatically; the existing lobby, preview, readiness and shared play flow then continues. Failed replacements keep the current lobby and game.

This governs support for [issue #238](https://github.com/TuringTestee/retro-coop/issues/238), separate from #208; the plan was independently reviewed and merged in [PR #240](https://github.com/TuringTestee/retro-coop/pull/240). The automatic selection rule below follows the requested automatic loading without another picker.

## Journeys

- **Drop:** a host in an open, unstarted lobby drops a ZIP onto the current game area. Existing status feedback shows upload, extraction and preparation. Success displays the extracted game's title and preview; members acquire the extracted NES bytes, ready and play with the host. Completion is synchronized host/guest play.
- **Picker:** the same host chooses a ZIP in the current Add game file chooser. Both entry points call one preparation function and have the same success and recovery. Keep one chooser and drop target; update their existing file hints and accepted extensions to include `.zip`.
- **Recovery:** a failed, cancelled or superseded attempt never replaces the current local worker, preview, room fingerprint or shared blob. Explain size, damaged archive, missing NES game, unsupported cartridge or service failure in the current status area. The chooser/drop target permits another attempt; successful retry completes the same journey. Leaving, losing membership, starting shared play or a newer selection invalidates pending work.
- **Existing paths:** ordinary `.nes`, included and saved games retain their existing behavior. Where the same chooser is used for local play, ZIP uses the same server extraction stage followed by local NES preparation; server unavailability explains failure and preserves the active local game. Shared-play replacement restrictions remain authoritative.

## Automatic extraction

One shared constant defines the compressed limit: strictly less than 2,000,000 bytes (2 MB), for both entry points and the server. Reject the exact boundary and larger bodies while receiving, including dishonest lengths. Extracted NES bytes retain the configured `RomStore` file limit (currently 64 MiB) and existing cartridge/emulator admission; archive size does not raise or reduce that limit.

Automatic rule: order safe regular `.nes` entries by normalized case-folded path, then exact path as a tie-break, and select the first. Ignore ordinary unrelated files and directories without inflating them. Attempt that game's normal admission and emulator load; if it fails, report failure rather than silently selecting another. The title uses the selected entry's basename through the existing NES title sanitization, never the outer ZIP filename. No archive selection UI.

Use a maintained ZIP parser with bounded central-directory traversal and streaming selected-entry extraction. Support ordinary stored/deflated ZIPs and nested directory names. Reject encryption, unsupported compression, duplicate normalized names, inconsistent local/central metadata, corrupt data/CRC, absolute or traversal paths and nonregular entries. Never extract archive paths onto disk: private scratch names are generated by the server. Enforce actual inflated bytes and parser bounds within the compressed-byte budget, the existing 300-second preparation deadline and 30-second idle-progress limit, and cancellation; do not trust advertised sizes or compression ratios. Bound concurrent extraction with the existing upload concurrency budget and account scratch/archive/output bytes in the existing storage capacity budget. Do not inflate unselected entries or recursively unpack nested archives.

## Existing interfaces and smallest extension

The authoritative chain is `main.tsx` selection → `Player.load` → `RoomClient.selectLobbyGame` → `beginGameSelection` → authenticated `PUT /rooms/:id/rom` → `RomStore.upload` → `confirmGameSelection`. `packages/contracts/src/fingerprint.ts` owns structural NES admission and identity; the pinned emulator owns hardware support. `RomStore` owns private blob capacity, admission and cleanup; members use its membership-authorized download and verified cache flow.

The PUT requires a browser-derived NES fingerprint and exact NES length before it receives bytes. Add one authenticated, origin-checked extraction POST before this chain, returning only the selected raw NES bytes plus a validated filename, byte count and SHA-256. Obtain the existing coordinator session first, including local play. Apply the coordinator's admission, rate and resource controls; ZIP preparation grants no lobby mutation or member download access. Keep the response private and uncached. The browser checks the response bounds/hash, creates an NES `File`, and runs the existing NES fingerprint/emulator preparation. Server extraction is mandatory; browser ZIP libraries are unnecessary.

For a lobby selection, upload that extracted file through the existing PUT and commit contract. This intentionally transfers the raw NES back once: it avoids another persistent artifact/token store or an alternative room admission protocol. Server and browser verify the same extracted identity. Guest sharing, catalog recognition and remembered imports continue to refer to NES bytes and identity, never ZIP bytes. Scratch archive/output files are deleted after response completion, disconnect, cancellation, error, deadline or shutdown; startup cleanup covers abandoned private scratch files.

Extend the current candidate worker lifecycle so lobby preparation can finish its normal upload/confirmation before committing the candidate locally. Today `Player.load` terminates the previous worker before `selectLobbyGame` uploads; retaining it until shared preparation succeeds is required for failed replacement recovery. Preserve existing server pending-blob promotion and cancellation; use selection generations and room revisions to reject stale completion. Keep this lifecycle shared by raw NES and extracted NES rather than introducing a second player. Prepare preview/battery before the final confirmation; after acknowledged confirmation, local commit must be immediate and nonfailing. Reconcile a lost confirmation response using the existing selected intent before cancelling or reporting failure, so server and local state agree.
