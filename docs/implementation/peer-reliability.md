# Relay policy-change reliability follow-up

Peer connections sometimes timed out after a guest’s first message was discarded below the JavaScript send call. The guest now waits for the host’s challenge before sending its own, avoiding that early-send window without extending deadlines. This follow-up retains observed failures and tests recovery while preserving the room, original reservation, local game and Relay only policy. The original policy-change CI failure lacks enough evidence to prove it had the same cause.

## Observed send loss and bounded repair

The first integrated full local run then [reproduced the missing guest probe](evidence/peer-reliability/local-native-send-failure.json) during retry after the connection deadline. Both suppression flags were false and their counts zero. The guest probe’s send returned normally and increased bufferedAmount from 0 to 72; its later reply also returned normally. Native stats counted only one sent message, and the host received only the reply. This places the observed loss below the JavaScript wrapper; it is not an injected failure. A single further stderr-instrumented run passed in 65.17s without a native error, ending exploratory reruns.

Pinned Chromium 145.0.7632.6 [remote-channel delivery](https://chromium.googlesource.com/chromium/src/+/refs/tags/145.0.7632.6/third_party/blink/renderer/modules/peerconnection/rtc_peer_connection.cc) forces the Blink channel open before dispatching the event. Its pinned libwebrtc revision’s [OnDataChannelOpenMessage](https://webrtc.googlesource.com/src/+/b47e68e6966d5a5a0e4bc861ff364221600f31c3/pc/data_channel_controller.cc) notifies the observer before posting native OnTransportReady. [SendImpl](https://webrtc.googlesource.com/src/+/b47e68e6966d5a5a0e4bc861ff364221600f31c3/pc/sctp_data_channel.cc) rejects non-open native state; [Blink’s asynchronous completion](https://chromium.googlesource.com/chromium/src/+/refs/tags/145.0.7632.6/third_party/blink/renderer/modules/peerconnection/rtc_data_channel.cc) logs that error without returning it to JavaScript. An early guest send racing native readiness is a source-backed inference consistent with observed loss, not a captured native error or proof about the original policy-change incident.

PeerConnection remains the sole transport-handshake owner. The host initiates on its locally created channel’s open event; the guest sends its challenge only after a valid inbound host challenge. Both peers still require their own nonce reply and must reply to the other nonce before acknowledging connection. No timer, retry loop, repeated probe or late handshake message is introduced. Existing epoch and malformed-message guards remain. A real-browser timing model discards guest probes before the first inbound message: the old protocol times out, while the repaired protocol avoids that send window and connects. This model is labeled separately from the real native-loss trace. The original full workload and explicit relay-failure Retry scenario remain, with this regression added rather than substituted. [Old-protocol failure](evidence/peer-reliability/ordered-before.json) and [current full result](evidence/peer-reliability/ordered-after.json) demonstrate the change; [validation details](evidence/peer-reliability/ordered-validation.json) retain the corrected guest-suppression expectation and current core digest. The repaired suite passed in 63.92s. Inspected [timeout](evidence/peer-reliability/ordered-policy-failure.png) and [successful relay Retry](evidence/peer-reliability/ordered-policy-retry.png) show the integrated UI.

## Historical recovery proof

The current sample is bounded to one full run against unchanged production code at `4e9ef75e0242094edb6155bdcd9420a610e3c7ec`, with this PR's additional test scenario. [Exact environment and core digest](evidence/peer-reliability/environment.json), [results](evidence/peer-reliability/retry.json), and inspected [failure](evidence/peer-reliability/policy-failure.png) / [retry](evidence/peer-reliability/policy-retry.png) are retained. Chromium 145.0.7632.6 completed the expanded suite in 66.63s with no unexpected failure. No batch is repeated until green: an unexpected failure stops the run and retains the existing bounded redacted diagnostics for inspection.

The original direct, forced-relay, reload, capacity denial/retry, policy change and both 15/20-second deadline workloads remain intact. A new test-only injection suppresses application transport probes after a further guest Standard-to-Relay change while the host requires relay. It waits for the actual coordinator timeout, checks both clients' failed state, selects Stay, restores probe delivery, then clicks Retry. The independent observations are unchanged room ID and reservation timestamp, unchanged paused host pixels, both peers' relay-only configurations, and real selected relay candidates with bidirectional bytes after retry. There is no direct fallback. The injection demonstrates recovery from this class of failure; it is not the original CI failure's cause.

The test's connected predicate now requires authoritative room status to be connected as well as the visible route. This avoids treating a local route announcement before the second acknowledgement as completed admission. It strengthens evidence sequencing and is not claimed as a runtime repair. The only production change is the role-ordered handshake above. Rooms remains the membership/lease publisher, PeerBroker the negotiation/relay owner, and contracts/peer.ts the privacy/limits owner; the test adds no competing production rule.

Reproduce using the README's pinned tools: `npm ci`, `sh scripts/foundation/prepare.sh`, `npm run build`, then `python3 scripts/peer/browser_smoke.py --output /tmp/peer.local.json` with Playwright 1.58.0's Chromium and coturn 4.6.1 available. `--turnserver` supports an unprivileged extracted binary; `--chrome` is an alternate browser run and must be labeled as such. Only application game gain is muted. Existing CI runs the full expanded suite under its 120-second command bound and shared 30-minute presubmit deadline. Full generic preflight is run after committing source and evidence; its current output is published on the PR, avoiding the prior mistake of checking before adding raw evidence.
