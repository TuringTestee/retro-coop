# Create Game and local ROM library delivery plan

## Sources and review snapshot

At the snapshot, `main` is `b5a5fb0`; `RoomPanel.tsx` renders the inline host bar and automatically calls `host()` after `LocalPlayer.load`, while `saves.ts` stores only downloaded verified ROM bytes by SHA-256. No implementation of this amendment has begun.

## Architecture and reuse

1. **Separate page state:** Give the app an explicit Public rooms / Create Game / waiting room / play view state. Route the Public rooms header's single **Create game** action to the setup page; browser Back and **Back to rooms** return to the same directory state. Invitations still open their own room preview. Remove the inline host bar and any duplicate setup file picker from the player panel. Keep the existing directory, room client, waiting room, and gameplay owners.
2. **One browser ROM library:** Extend the existing `saves.ts` IndexedDB `roms` owner to hold a bounded local display label, source, last-used time, and optional small preview beside verified bytes, all keyed by exact SHA-256. Migrate existing downloaded records without losing bytes. Bundled games are derived from the verified catalog manifest and appear once without duplicating their bytes in IndexedDB. A local import and guest download of the same hash update one entry. Public room metadata still uses the neutral generated room name; local filename/label/preview never leaves the browser. Local data deletion and clear generation guards remain authoritative, including cross-tab races.
3. **Safe selection:** Add file validates through the existing cartridge/fingerprint path, computes exact SHA-256, then stores a verified copy when possible. Selecting a saved row rehashes bytes and checks size before enabling **Create room**. A denied/quota write leaves the validated file in tab memory with an honest notice. A corrupt/evicted record cannot create a room. Reuse `acquireVerifiedRom` where it fits; keep its per-record and whole-store deletion generations rather than writing a second ROM cache.
4. **Deliberate creation:** Decouple `LocalPlayer.load` from automatic `RoomClient.host()`. File or library selection prepares local bytes and preview only. **Create room** is the sole trigger for the existing hidden create → private upload → server verify → publish transaction for custom files. For bundled games, **Create room** claims one existing 0/2 offer through the proven atomic `claimCode` path; it does not upload a duplicate asset or create a second kind of included room. If no healthy offer is available, show that state beside Create and return to the room browser for another game. The two included games remain ordinary visible lobbies, and the service replenishes a claimed offer. Cancel or failure returns to selected setup without a public ghost row; switching files cannot replace an active room implicitly.
5. **Real preview:** Capture a small frame only after a game has actually rendered nonblank content, associate it with the exact hash, and update last-used on actual play/hosting. Restrict encoded dimensions/bytes and reject malformed stored preview data. When there is no usable frame, render text “No preview yet”; do not show a blank image or invent cover art. Preview is display only, never another way to select/host.
6. **Focused UI:** Build Create Game as its own component/page with recent preview, unique Your games list, Add NES file, selected-game summary, Public/Unlisted choice, and Create room. Keep Local data deletion in Settings. Make status, focus, disabled reason, keyboard selection, and narrow layout match the wireframe. Remove old inline host copy and stale instructions from the public entry point and README.
