# Room access and automatic routing implementation

## Authority and order

The [design amendment](../design/room-access-and-routing.md), [minimal room journey](minimal-room-journey.md) and [issue #169](https://github.com/TuringTestee/retro-coop/issues/169) govern this slice. Merge this plan before product implementation. The host/guest/member and five-slot authorities remain as built; password verification is an admission check **before** slot reservation, ROM transfer, chat, signaling or peer setup. Neither an invitation code nor a directory result grants membership. The existing all-occupied initial Start gate and exit-before-directory path apply after admission.

## Access model and lifecycle

- Replace new-room `public|unlisted` with `public|protected` in one canonical room contract. Both appear in directory/search with the same allowed game, host, occupancy and availability metadata; protected rows add only a lock/Password required label. Exact room code and invite link locate either room. Remove newly created unlisted rooms and invitation-only admission. An old unlisted room from a live older coordinator remains unlisted until it closes or expires; never publish it during rollout. Expired legacy invites fail clearly.
- Protected creation requires a nonempty password under a bounded length/strength rule appropriate for a shared game room (at least 8 characters, up to 128 Unicode characters; no composition rule or silent truncation). Validate before creating or publishing the room. Store only a per-room salted, slow password verifier in ephemeral coordinator memory; never persist or log the plaintext or derived secret. Use a maintained password KDF and safe comparison. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) inform the verifier, input limits, throttling and error behavior. This is room access, not an account password.
- Put the protected credential gate at the shared coordinator reservation owner (`Rooms.reserve` or its single replacement) so directory Join, exact code, invite, late observer and any other first-admission caller cannot bypass it. Verify before allocating any slot, reservation/lease, file token, peer credentials or chat membership. Bind successful admission to the current room access revision and the same authenticated member/reservation lifecycle already used for reconnect. A reconnect with a valid existing membership token does not need to re-enter the password; a fresh join does. A wrong password or stale access revision has no side effects on room occupancy or other members. Never put the password in URL, browser storage, directory/event payload, analytics, logs or chat.
- Host access changes and password changes are one atomic visibility command with an access revision: set a verifier when changing to protected, replace it on password change, and clear it when changing to public. New joins see the new rule; pending unadmitted attempts against the old revision fail and can retry. Existing admitted members remain, including their voice/game links; the host can remove them separately. A protected-to-public change needs the existing exposure confirmation in plain language. A failure preserves the old rule. All host-only commands validate current membership and revision.
- Throttle failed attempts by trusted network address and room across WebSocket sessions, plus a bounded global verifier-work budget; the existing per-session room-command rate limit is insufficient for cross-session guessing. Do not let an attacker lock every visitor out of a room. Return a retry time on throttling; do not turn a bad password into a slot reservation. Rate-limit unknown codes and expired links too. Keep denial messages useful to a person without returning password/verifier details. Bound payload size before KDF work; run the slow KDF asynchronously behind a finite queue/concurrency limit so attempts cannot block the coordinator event loop or grow CPU/memory without bound.

## Automatic route policy

Remove `ConnectionPolicy` as a visitor preference from the directory, creation, invitations, waiting room, Settings and protocol commands. The coordinator and peers negotiate the same automatic policy for all members before gathering candidates. Prefer direct peer paths when viable within existing connection deadlines, with TURN relay fallback when direct cannot connect; do not add a serial direct-only timeout or claim that offering a relay candidate means relay was selected. If relay is unavailable after direct fails, retain the room and give Retry/Leave. Existing live strict relay-only sessions keep that policy until they end or are cleanly closed during rollout; do not silently rewrite an active peer epoch. No UI action changes the route policy midgame.

This replaces the prior user-selected relay-only protection because the owner explicitly clarified that Standard/Relay-only is not a user privacy choice. The public Privacy/Help text states that direct peer connections may expose network addresses to room participants and does not promise anonymity from the service or relay. No route terminology, address disclosure paragraph or performance counters occupy the ordinary Join/Create/play path. Keep privacy-safe logs without candidate addresses or SDP. The selected route remains observable to diagnostics and test instrumentation; ordinary users see only connection progress, failure and recovery.

## Replacement inventory and delivery

The authoritative owners to change are room contracts, coordinator admission/visibility, client directory/Create Game/invitation/Settings, peer policy negotiation, and their shared tests. Remove `unlisted` creation and old Standard/Relay-only controls, per-user policy storage and policy-change commands after callers migrate. Preserve exact public code collision handling, five-slot capacity, ROM authorization, join leases, reconnect, chat/voice and no-background-session behavior. Do not retain a second password-bypass join through invitation, code search, late observer admission or reconnect. Keep only one access rule and one automatic peer-routing rule.

## Evidence and failure gates

Run the README pre-flight and existing CI gate. In real browsers, create and join public/protected rooms from search, exact code and invitation; check wrong password, throttled Retry, stale/closed room, password change during Join, full final-slot race, reconnect with a valid member token, and five-member/late-observer admission. Verify no slot, ROM byte, chat, peer credential or signaling reaches a rejected joiner. Inspect directory payloads and URLs for absence of plaintext/verifier; inspect logs for no password, candidate address or SDP. Test direct success, forced relay, direct failure with relay fallback, relay exhaustion, reconnect and route changes across five-member pairs; inspect selected candidate pairs and positive bytes, not just UI labels. Check no current strict relay-only session silently becomes direct during rollout. Capture normal and recovery screenshots under #158's fixed-region bounds. This planning PR needs document checks; browser behavior is proven by implementation, not by this text.
