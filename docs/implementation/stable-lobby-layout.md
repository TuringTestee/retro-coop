## Existing owners and repair approach

`apps/client/src/style.css` repeats and overrides `.directory-panel`, `.playing`, `.room-panel`, and narrow/short media rules. Several outer grid tracks are `auto`; conditional notices, flex wrapping, and varying content lengths can therefore move later regions. `RoomPanel.tsx` conditionally inserts acquisition, start, connection, and confirmation blocks. `CreateGame.tsx`, `DirectoryPanel.tsx`, `VoiceControls.tsx`, `ChatPanel.tsx`, and `main.tsx` supply other changing-content boundaries. Inspect the integrated #157 versions before editing; its new slots are the single room-row owner.

Define a coherent set of CSS grid/flex regions per existing screen and responsive profile. Derive header, content, status, and action dimensions from viewport/profile tokens, not message lengths or loading flags. Give shrinking grid children explicit minimum-size behavior and put overflow on the intended content region. Reserve the canvas aspect ratio and controls' label-change width. Keep all five slot rows mounted with deterministic per-profile row bounds; loading, empty, closed, occupied, pending, and failed states reuse their inner status/action cells.

Render stable status and action containers even when their content is empty. An empty reserved region must not announce fake status or add focusable placeholders. Replace inline confirmation contents inside their existing action region; preserve semantics and focus restoration. Longer messages may wrap and scroll within a bounded accessible status region, but must remain fully available. Keep live-region semantics without repeatedly announcing unchanged content. Do not force stable screenshots by truncating actionable explanations or turning off real feedback.

Keep the desktop play rail's immediate microphone and Leave actions in reserved regions, with connection feedback and other details in their allocated content areas. In particular, pausing must not move Leave partly outside its rail (#131). For narrow/short/zoomed profiles, retain the existing stacked screen order and declare the content scroll owner explicitly. Scroll ranges must include the complete final action and focus outline. Avoid accidental nested clipping and document which regions scroll; keyboard focus must reveal its target without changing layout or scrolling a hidden page. Scrollable text-only regions need keyboard access and meaningful accessible names, without empty focus stops. Do not use smaller text, hidden controls, or global overflow suppression as a fit fix.

Remove superseded CSS declarations and conflicting breakpoint exceptions as each owner migrates; do not append another competing layer of overrides. Update any current layout instructions that still describe content-driven expansion. Keep historical wireframes as history with a scoped link to this amendment when necessary. This work has no reason to change room protocols, voice permission/mute semantics, ROM admission, or navigation.

## Measured verification

Extend existing browser journeys under `scripts/rooms/` and the voice/sidebar probes instead of adding a parallel mock application. Launch through the README public entry point on the exact candidate. Use real coordinator/client states with controlled delays and failures. Add stable semantic selectors to region owners where needed; do not use generated text or fragile positional selectors as geometry identities.

For each transition, record `getBoundingClientRect()` for the header, content/canvas frame, status containers, primary action, applicable slot rows, voice action, and Leave. Compare x/y/width/height before, during, and after at the same viewport, zoom, and scroll offset. Allow at most one CSS pixel of rounding per bound. Sample during delayed operations and immediately around DOM/state updates; waiting only for the settled final state cannot prove absence of movement. Capture early page loading/font/image transitions too. If the user scrolls, normalize bounds to the containing scroll region and separately verify container bounds; resetting scroll between samples cannot hide an unwanted scroll jump.

Check control rectangles against the visible intersection of viewport and all clipping ancestors, including full button and focus-outline visibility for #131. Check overlap, horizontal page overflow, and inaccessible scroll endpoints. Exercise tab order, focus return after cancel/removal/Back, and keyboard scrolling; geometry alone cannot establish accessibility. Content that legitimately changes inside a reserved region need not have identical glyph bounds, but its owning region and sibling controls must not move. Browser layout-shift metrics may supplement these assertions; they do not replace them because user-input shifts and clipping can escape those metrics.

| State matrix | Required transitions and evidence |
|---|---|
| Discovery/invitation | Loading → live, empty results, long room/host names, stale/network error → retry, full/closed room, and changing page counts. Compare list frame, status, pagination, Join/Back, and header. |
| Create Game | Empty/saved/included/local selection, file checking/loading, upload progress, storage warning, download/upload failure, retry and cancel. Compare library/options/status and Create/Cancel bounds. |

| Playing | Active → paused → resume; direct/relay feedback; connection loss/recovery; chat growth; voice off/requesting/on/muted/denied/retry and push-to-talk; host-as-observer. Compare game frame, rail regions, microphone action, room actions, and connection feedback. |
| Short-window regression | Exact 1366×682 host and guest paused views from #131, including the connection message. Supply matched before/after screenshots and full Leave bounds assertions. |
| Secondary tasks | Settings, Local data, Saves, Rewind, Help, release notice; long content; inline confirmation/error; Back with preserved focus. Compare header/content/action regions and exercise final scroll endpoints. |

Run wide desktop (1440×900), reported regression (1366×682), short desktop (1024×600), and a narrow desktop profile on each affected screen. Also test enlarged browser zoom at 200% and an effective 320-CSS-pixel content width, recording physical viewport, actual CSS viewport, zoom, and device scale separately. Viewport resizing alone must not be reported as browser-zoom evidence. These are desktop accessibility/reflow checks, not a new mobile-platform support promise. Use a smaller pairwise subset for all transient-state combinations, but every screen must cover its applicable loading/error states and every layout profile must cover keyboard/overflow; #131's exact cases and five-slot waiting/playing geometry are mandatory.
