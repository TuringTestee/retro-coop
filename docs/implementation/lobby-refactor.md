# Lobby refactor: architecture and delivery amendment

**Status:** Proposed planning snapshot for [the human direction](../design/lobby-refactor.md). No affected implementation is authorized until this exact reviewed revision receives user approval and its governing documents merge. The existing epic and issues continue to own unaffected work.

## Current code and conflict

At this review snapshot, `apps/coordinator/src/rooms.ts` stores only rooms whose host is a connected `Session`; `create` provides a fingerprint and `joinCode` reserves the guest place. `RoomPreview` in `packages/contracts/src/rooms.ts` permits only 1/2 or 2/2 occupancy. `apps/client/src/RoomPanel.tsx` renders two special catalog launchers plus a file launcher and automatically hosts when a local file loads. `DirectoryPanel.tsx` joins only waiting 1/2 rooms. `GameSession.ready` in `apps/coordinator/src/gameplay.ts` starts eligible shared games automatically and rejects a progressed host with “Shared late join is not available yet.” These concrete owners must change; styling alone cannot deliver the new behavior.

The approved [catalog amendment](included-games.md) and [platform plan](browser-nes-platform.md) still prescribe those old interaction rules. Planning PR #65 is merged; D19/#23 and D15/#19 are closed, but integration and current-head evidence must be confirmed before dependent work is dispatched. D12/#16 is also closed, yet the coordinator rejects progressed late join. The essential refactor keeps that admission closed; later join requires separate planning and evidence. The new [human amendment](../design/lobby-refactor.md) supersedes the conflicting interaction rules only after its own approval and merge.

## Architecture and reuse decisions

1. **Represent empty offers separately from human rooms.** The coordinator owns exactly one public 0/2 offer per configured, healthy included asset. An offer carries a generated room ID/code and catalog identity but no fake host session or gameplay state. Extend the preview contract to represent 0/2 and No host; a claimed offer becomes a normal room at the same ID/code. The first claim is one atomic coordinator mutation that assigns Host/P1, binds the pinned catalog fingerprint, and replenishes the empty offer. Reuse directory publishing, code uniqueness, session tokens, authorization, and room lifecycle. Keep offers in a separately bounded two-entry pool; only claimed/human rooms consume the existing 20 active-room limit. At that limit, retain the 0/2 offer as unavailable with a capacity reason and re-enable it when a room closes. Keep offer publication behind a default-off coordinator capability until a claim-capable client is integrated and enabled in the same release. A client without claim capability must not render or act on a 0/2 preview. Do not publish an offer for an unavailable asset or imply that server emulation is running.
2. **Keep browser-owned play.** After claim, the first browser downloads and verifies the included file, then hosts the peer connection. An asset failure must release or clearly retain the claim with a bounded retry and honest directory state. Human-created rooms continue through the existing create/confirm flow, with no ROM bytes, local path, or filename in public metadata. Exact matching catalog files may reuse verified downloads; other guests select their own file. Unlisted rooms remain outside directory/code lookup.
3. **Make Start host-controlled.** Add an authoritative, idempotent Start command tied to the current host, room identity, and membership. Loading an included or local file prepares the browser without starting a new room/game. A host may Start when locally ready. With no ready guest, Start begins solo in that room and closes its guest admission; with a ready guest, it enables the existing acknowledged shared barrier. A preparing guest does not block the host: Start releases that pending place with a clear message to the guest before solo play. Reject stale, guest, pre-ready, and repeated commands without starting another timeline. Preserve D15's controller ownership and From Below's shared-P1 behavior. A playing 1/2 room is visible but has no Join action in this delivery.
4. **Use one client path and one directory.** `RoomPanel` owns room state; `DirectoryPanel` renders all public previews with state-specific single actions. Remove catalog cards, Show lobbies filters, duplicate host controls, and early play controls. A 0/2 row says Join as host; a waiting 1/2 row says Join; a playing 1/2 row says Join unavailable. Keep Public/Unlisted and Standard/Relay only beside the direct file drop/picker and public Join actions. A valid local file is checked and creates a room immediately with a generated neutral label; do not add a name form or second Create button. Explain the guest's exact-file need on the custom row before Join. Put role, Start, invitation, room actions, and recovery in the room; keep chat usable in occupied waiting rooms before ROM selection. Hide unusable invites after solo Start and make the game canvas dominant. Keep accessible keyboard/focus behavior, pagination, stale-result protection, and supported viewport bounds.
5. **Keep restart and shortage honest.** Startup and cleanup restore the two empty offers when their assets and capacity permit; human rooms still close on restart. A first-join race has one host; the loser sees the updated 1/2 row or a new 0/2 offer. Capacity/rate limits cannot create ghost offers or rooms. Operator removal, moderation, invite secrecy, relay privacy, and anonymous identity rules continue to apply to claimed rooms.

## Review snapshot and remaining limits

This amendment reuses the current React/Vite client, Node coordinator, protocol validation, catalog manifest, peer transport, and controller owners. It defers the existing late-join owner and adds no database, dedicated game process, accounts, or user-file distribution. The two lightweight empty offers do not consume the 20 active-room slots, but their directory/signaling cost still belongs in the existing measured operating ceiling. Real browser behavior, content qualification, independent network play, and accessibility remain to be evidenced by the delivery issues.
